\section{JWT}

\begin{frame}{Como validar sem depender do servidor? (JWT)}
\note{Uma característica importante do JWT é que ele é autocontido. Depois que eu emito esse token, qualquer serviço que consiga validar a assinatura pode aceitá-lo até o momento em que ele expire. Eu não preciso consultar o Authorization Server a cada requisição.}
  \begin{center}
    \includegraphics[width=0.8\textwidth]{jwt}
  \end{center}

  \vspace{1em}

  \begin{center}
    \textit{Stateless para validar, difícil de revogar antes da expiração.}
  \end{center}
\end{frame}

\begin{frame}{Quem pode usar esse token? (Bearer)}
  \begin{itemize}
    \item Bearer Authentication é um mecanismo de autenticação HTTP em
    que o cliente envia um token junto com a requisição.

    \item O nome ``Bearer'' significa literalmente: ``Quem portar esse
    token pode usá-lo.''

    \item A API não verifica quem está segurando o token; ela apenas
    verifica se o token é válido.
  \end{itemize}
\end{frame}

  Atividades de configuração se tornam morosas, desenvolvedores se tornam gargalos da operação

  \begin{itemize}
    \item Emitir uma API-KEY
    \item Revogar uma API-KEY

  \begin{center}
    \textit{O problema deixou de ser ``como validar um token?'' e passou a
    ser ``como gerenciar identidades, credenciais e permissões?''}
  \end{center}
\end{frame}

\begin{frame}{Como delegar acesso sem distribuir a credencial? (OAuth2)}
\note{Tudo isso que acabamos de ver — emitir, revogar, blacklist, controle de acesso — hoje é feito manualmente por cada equipe, sem um padrão em comum. O problema agora é: como delegar acesso sem distribuir a credencial original? O OAuth2 não resolve isso com uma técnica específica; ele fornece um framework de autorização, com papéis e fluxos padronizados, pra essa delegação.}

OAuth 2.0 é um framework de autorização que permite que uma aplicação obtenha acesso limitado a recursos de outra aplicação, sem precisar conhecer as credenciais do usuário.

Ele define papéis, fluxos e mecanismos para delegar esse acesso através de \textit{access tokens}.

\begin{center}
\textit{OAuth 2.0 não é, por si só, um protocolo de autenticação.}
\end{center}

\end{frame}

\note{Aqui o segredo já não dá acesso direto à API: ele é usado só pra obter, junto ao Authorization Server, um token com escopo e duração controlados. Isso já é uma melhoria operacional grande em relação à API Key estática.}

\begin{frame}{Access vs Refresh Token}

    \begin{columns}[T,onlytextwidth]

        \column{0.5\textwidth}

        \textbf{Access Token}

        \begin{itemize}
            \item Curta duração
            \item Enviado para Resource Servers
            \item Representa uma autorização
            \item Pode ser JWT
        \end{itemize}

        \column{0.5\textwidth}

        \textbf{Refresh Token}

        \begin{itemize}
            \item Longa duração
            \item Enviado apenas ao Authorization Server
            \item Usado para obter novos Access Tokens
            \item Deve ser protegido com mais cuidado
        \end{itemize}

    \end{columns}

\end{frame}

\section{OIDC}

\begin{frame}{Quem é o usuário autenticado? (OIDC)}

    OpenID Connect é uma camada de identidade construída sobre
    OAuth 2.

    Ele permite que uma aplicação obtenha informações sobre o
    usuário que foi autenticado, através de um \textit{ID Token}.

    \begin{center}
        \textit{OAuth 2.0 responde ``o que pode acessar?''.
        OIDC responde ``quem está autenticado?''.}
    \end{center}

\end{frame}

\begin{frame}{Com que confiança o usuário autenticou? (AMR/ACR)}
\note{Na nossa aplicação, o contexto de autenticação influencia o que o usuário pode fazer. Por exemplo: um usuário que não autenticou com OTP não pode realizar determinada operação. O AMR permite que o serviço saiba quais métodos de autenticação foram utilizados.}
        \begin{itemize}
            \item \textbf{AMR}: como o usuário foi autenticado
            \item \textbf{ACR}: nível ou contexto de confiança da autenticação
        \end{itemize}

        \vspace{1em}

        \begin{center}
            \textit{A autenticação pode ter contexto, não é apenas
            ``logado'' ou ``não logado''.}
        \end{center}

\end{frame}
